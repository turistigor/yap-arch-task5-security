<summary>в группе сервисов ЖКУ:</summary> Как сказано в описании, функционал умного дома уже присутствует в системе и доступен клиенту через мобильное приложение. Предполагаю, что он реализован в контейнере tenant-core-app.
Новые функции, которые не требуют работы с биометрией будем добавлять туда же так как у этого контейнера уже существуют механизм получения клиентских данных из сервиса CRM (он не кажется оптимальным, но задачи менять его сейчас нет).  

Для работы с биометрией будет создан сервис biometry, основной задачей которого будет сопоставление присылаемых материалов (фото) с образцами в БД клиентов и вынесение вердикта о разрешении на доступ. Для получения информации о разрешениях идентифицированного клиента предполагается использовать REST API в сервис CRM (аналогично сервису tenant-core-app).  
В качестве альтернативы можно было бы реализовать весь биометрический функционал в tenant-core-app (который отвечает за текущий функционал умного дома), но такое решение ведет к увеличению ответственности этого сервиса, а также осложняет самостоятельное использование биометрии для других задач в будущем.

Описание взаимодействия (firewall и витрина сокращены):
- Авторизация перед другими запросами:
    - Умный дом -- GET /token grant_type=client_credentials, payload:{partner_id, partner_secret} resp:{token: hash} --> auth-service-1
- Домофон -> Фото лица -> Запрос на открытие
    - Умный дом -- GET /ops?device_id&op=open payload:{face_photo} resp:{allowed: true/false} --> biometry
- Шлагбаум -> Фото номеров машины -> Запрос на открытие
    - Умный дом -- GET /ops?device_id&op=open payload:{plate_number_photo} resp:{allowed: true/false} --> biometry
- Собственник
    - Домофон -> Запрос на открытие
        - Умный дом -- GET /ops?user_id=&device_id&op=open resp:{allowed: true/false} --> PropDevelopment
    - Шлагбаум -> Запрос на открытие
        - Умный дом -- GET /ops?user_id=&device_id&op=open resp:{allowed: true/false} --> PropDevelopment
- Гость
    - Домофон -> Звонок
        - Умный дом -- GET /ops?device_id&op=call resp:{allowed: true/false} --> PropDevelopment

Требования:
- Общие требования
    - Протокол взаимодействия:
        - HTTPS с TLS 1.3.
        - Шифрование современными надежными алгоритмами (например, ECDHE).
        - Использовать действительные TLS-сертификаты, выпущенные доверенным удостоверяющим центром, и своевременно их обновлять.
    - Авторизация в PropDevelopment: 
        - Протокол OAuth2.
    - Все запросы должны логироваться (без чувствительных данных) с обеих сторон.
- К партнеру:
    - Соответствие защиты данных 152-ФЗ.
    - Протокол взаимодействия:
        - При установке HTTPS-соединения проверять подлинность сертификата сервера.
    - Авторизация в PropDevelopment:
        - Необходимо получить access_token и время его жизни в соответствии с OAuth2 с использованием соответствующих секретов.
        - Секреты должны храниться в защищенном хранилище (например Vault) с шифрованием.
        - Необходимо обеспечить регулярную ротацию секретов.
    - Запросы к PropDevelopment:
        - Необходимо добавлять access_token в каждый запрос.
        - Необходимо учитывать, время жизни access_token и своевременно его обновлять.
        - Корректно заполнять заголовки запроса (например, Content-Type).
    - Ошибки
        - Обрабатывать ошибки с кодами 5xx с экспоненциальной задержкой повторных запросов.
        - Не повторять запросы, возвращающие ошибки авторизации (401, 403), без нового токена.
- К PropDevelopment:
    - Протокол взаимодействия:
        - Настроить веб-сервер для приема входящих соединений только только по HTTPS с TLS 1.3.
        - Необходимо обеспечить наличие действительного сертификата, подписанного удостоверяющим центром.
    - Авторизация в PropDevelopment:
        - На основе данных токена принимать решение о разрешении или запрете конкретной операции.
        - При недостаточных правах возвращать возвращать ошибку (403).
        - Обеспечит безопасное хранение, ротацию и публикацию access_token.
    - Запросы к PropDevelopment:
        - Проверять подпись access_token.
        - Проверять срок действия access_token и возвращать ошибку (401) при необходимости.
        - Ограничить размер запросов.
        - Проверять корректность запроса (например Content-Type).
        - Предоставить полную и актуальную документацию к API.
    - Подготовка юридических документов, регламентирующих автоматический сбор биометрии (фото) на основании явного намерения пользователя, взаимодействующего с системой.
